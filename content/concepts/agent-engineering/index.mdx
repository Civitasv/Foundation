# Agent 工程总览

## 从一个任务看整个系统

假设你让一个 Agent 修改项目中的一处错误，并确认修改有效。它需要理解要求、找到相关代码、做出修改、运行检查，再根据结果决定继续修复还是结束。如果检查失败，下一步必须依据新的错误信息调整；如果缺少权限，系统需要停下来，而不是把猜测当作成功。

这件事把 Agent 工程的几个层次放在了同一条线上：**目标规定要达到什么，模型提出下一步，工具接触外部世界，运行时执行并保留状态，反馈让下一步有据可依。** 上下文决定模型能看到什么，权限决定系统能做什么，评测决定我们如何判断它做得怎样。

本文沿着这个任务打开系统，再向下连接模型和数学。你可以先读完建立全局图景，也可以在遇到具体问题时进入对应章节，读完后回到这里确认它在整体中的位置。

## 循环：让行动的结果进入下一次决定

一次模型回答只能给出当时条件下的输出。要完成一个需要探索的任务，系统需要反复取得信息、做决定、采取行动，并把结果写回状态。这里用下面的流程概括一个常见的模型驱动 Agent：

```text
目标与当前状态
      ↓
构造上下文 → 模型提出下一步
                  ↓
          检查请求与执行条件
                  ↓
              执行工具
                  ↓
        记录结果、更新状态
                  ↓
       继续 / 完成 / 暂停 / 失败
```

在修改代码的例子中，读取文件产生观察，修改文件改变环境，测试结果又产生新的观察。循环中的关键不是多调用几次模型，而是每次调用都能接上前一次行动造成的变化。停止也需要依据：检查通过、预算耗尽、用户中断和权限不足，是不同的结束或暂停原因。

[Agent 循环](/concepts/agent-loop/)展开这一控制结构。读它时关注三个问题：哪些状态需要保留，什么事件允许进入下一步，以及如何确定任务已经结束。ReAct 是将推理与环境行动交替组织起来的一项研究；这里的运行时视角还需要考虑执行、状态和终止条件。

任务路径完全确定时，固定工作流可能已经足够；需要根据运行中获得的信息调整路径时，才有理由把更多决定交给模型。自主程度是设计选择。

## 工具：把一个提议变成实际的行动

模型说“我已经运行测试”，不等于测试真的执行过。只有执行系统调用测试工具、拿到进程结果并记录下来，这句话才有外部证据。

工具调用可以看成有明确名称、参数和返回值的请求。例如，模型提出读取某个文件，执行层先验证参数与访问范围，再读取文件，把内容或错误返回给循环。**模型负责提出请求，执行层负责决定请求能否执行并报告实际结果。** 参数符合格式也不意味着行动一定被授权。

[工具调用](/concepts/tool-calling/)解释这条边界。它连接模型侧的结构化输出与系统侧的能力、校验、权限和错误处理。放回完整任务中，工具是获得新证据、改变项目状态的接口；工具返回值则是下一次决定的输入。

## 模型：在给定上下文中生成下一步

在许多基于语言模型的 Agent 中，模型接收任务说明、相关材料和工具结果，生成回答或工具请求。常见的自回归语言模型按 token 逐步生成：把已有序列变成内部表示，计算下一个 token 的分数，再通过选择策略得到输出。完整行为依赖许多步生成，单个 token 的概率不能直接解释成任务成功的概率。

对于 Transformer 模型，[自注意力](/concepts/self-attention/)是理解上下文如何参与表示计算的重要入口。一个 token 可以依据其他位置的信息更新自己的表示；在因果语言模型中，mask 限制它不能读取未来位置。Attention 是模型中的一个机制，完整模型还包含前馈层、残差连接、归一化等部分。

这也解释了上下文为何是工程问题：相关代码没有进入输入，模型就无法直接依据它做决定；工具错误被遗漏，后续生成可能建立在过时的信息上。把信息放进上下文只表示它可被处理，不保证模型会正确理解或使用它。

要看清这个机制，可以继续向下打开数学层。

## 数学：表示、变换、比较与分配权重

这些基础概念各自承担一项具体工作。把它们放回 Attention，就能理解它们为什么一起出现。

**向量描述表示。** 模型中的 token 表示通常是一组数。它们提供可以计算的坐标，而每个坐标不必对应一个人类可命名的语义。[向量](/concepts/vector/)从长度、方向和坐标建立直觉，为后面的变换与比较提供对象。

**矩阵描述线性变换。** 同一份表示可以经过不同的投影，形成用于查询、匹配和提供内容的 Q、K、V。[矩阵](/concepts/matrix/)解释如何把一组向量变换成另一组，以及矩阵乘法如何组织这种计算。

**点积给出比较分数。** 在缩放点积 Attention 中，query 与 key 的点积参与计算匹配分数。分数受方向和长度共同影响，因此不能把它简单等同于纯粹的方向相似度。[点积](/concepts/dot-product/)连接坐标计算、夹角和投影。

**Softmax 把分数变成归一化权重。** 原始分数可以为负，也不要求总和为一；经过 Softmax 后，可以用它们对 value 加权求和。[Softmax](/concepts/softmax/)讨论分数尺度怎样改变权重分配。Attention 权重用于混合表示，而输出端的 token 概率用于生成选择，两者处在不同的计算位置。

**概率分布描述不确定的选择。** 归一化、期望、熵和采样帮助我们理解输出分布及选择策略。[概率分布](/concepts/probability/)是阅读 Softmax 和生成过程的基础。概率较高表示模型在当前条件下更倾向于某个输出，并不保证输出真实，也不保证行动安全。

两条基础路径在自注意力中汇合：

```text
向量 → 矩阵 ─────┐
  └──→ 点积 ────┼→ 自注意力
概率分布 → Softmax ┘
```

这表示概念之间的依赖。你可以先理解系统如何使用模型，再按需要沿这些路径补足计算细节，无需把全部数学学完才开始观察一个 Agent。

## 系统：让一次成功变成可重复的行为

模型和工具接上循环后，还需要回答一些贯穿任务的问题。这些主题目前尚未有独立的详细章节，但它们属于全局图景的一部分。

**上下文与记忆。** 当前上下文是这一次调用能够读取的输入；运行状态和长期记忆可以保存在外部，并在需要时被选择进入上下文。在代码任务中，已修改哪些文件、哪些检查失败、用户有哪些约束，都可能需要保留。保存、检索和放入输入，是不同的步骤。

**检索与证据。** 文件搜索、文档检索和数据库查询帮助系统取得所需材料。拿到材料后仍要保留来源、确认适用范围，并处理互相矛盾的结果。检索负责提供候选证据，模型的回答不能替代对证据的核对。

**运行时与恢复。** 超时、重试、取消、并发和持久化决定循环能否稳定运行。读取文件失败通常可以重试；写入、提交或付款等有副作用的操作，则需要先确认是否已经执行，避免重复动作。这些问题应由明确的状态与执行规则处理。

**安全与权限。** 读取到的文件、网页和工具结果可能包含指令式文字，但它们是任务材料。执行系统需要区分材料与用户授权，并在能力边界上检查请求。风险越高的行动，越需要清晰的许可条件和可追溯记录。

**评测与可观测性。** 在这个例子中，最终修改是否正确、测试是否真的运行、是否改动无关文件，比回答听起来是否自信更能说明结果。任务评测检查目标是否达成；执行轨迹帮助定位是哪一步、哪份输入或哪个工具导致失败。成本和延迟也属于系统表现。

这些约束横跨整个循环。研究模型能力时可以聚焦局部；交付一个系统时，需要把它们一起放回任务中检查。

## 如何在总览与章节之间阅读

如果你想先理解 Agent 怎样工作，从[工具调用](/concepts/tool-calling/)进入，再读[Agent 循环](/concepts/agent-loop/)。前者说明一次动作怎样跨过执行边界，后者说明多个动作怎样通过状态与反馈连成任务。

如果你想理解模型内部怎样计算，先读[向量](/concepts/vector/)，再分别进入[矩阵](/concepts/matrix/)与[点积](/concepts/dot-product/)；另一条线从[概率分布](/concepts/probability/)进入[Softmax](/concepts/softmax/)。准备好这些基础后，在[自注意力](/concepts/self-attention/)把它们合起来。

目前向量、矩阵、点积和概率分布已有展开的解释与交互实验；Softmax、自注意力、工具调用和 Agent 循环仍是章节提纲，会继续补充。本文承担全局索引的作用，不意味着每个局部已经写完。

当你读完一个局部章节，可以回到前面的代码任务：这个概念改变了哪一步的理解？它解释的是模型中的计算，还是系统中的行动与约束？这两个尺度之间的来回，正是这篇总览与详细章节的连接方式。
